# PWA 更新与缓存

> 目标：用户已经把页面「添加到主屏」之后，每次发版他打开就是新版。

## 问题长什么样

代码已上传，服务器文件确认是新的，`curl` 抓下来也是新的，但用户手机上还是旧界面。

典型错误归因：「用户没清缓存」「让他重新装一下」「手机抽风了」——这三句都是放弃治疗。

正确归因：一定是**中间层**问题，排查顺序是 CDN → Service Worker → HTTP 缓存头。

## 根因：双层缓存自锁

这是 PWA 独有的坑，普通静态站不会遇到。

- 第一层：CDN 按 `.js` 后缀把 `sw.js` 缓存了（Cloudflare 默认 4 小时）
- 第二层：旧 SW 采用「缓存优先」，把旧 HTML 钉在本地

两层叠加形成一条**自锁死链**：

```
用户请求 → 拿到旧 SW → 旧 SW 返回旧 HTML
            ↑
      即使服务器上有新 SW，URL 相同被 CDN 缓存，用户也拿不到
```

于是用户**既看不到新页面，也拿不到能更新自己的新 SW**。

关键认知：**普通静态站的缓存问题会自愈（过期就好），PWA 的缓存问题不会自愈，因为 SW 本身也是被缓存的对象。**

## 三层解法（缺一层都可能复发）

### 第一层：改缓存策略

- 导航请求（`request.mode === 'navigate'`）→ **网络优先**，断网才回退缓存
- 静态资源（图标、字体）→ stale-while-revalidate
- `activate` 时删掉旧 cache，并 `client.navigate()` 让已打开的页面重新加载

### 第二层：版本化 SW URL（最关键，成本最低）

```js
navigator.serviceWorker.register('sw.js?v=8', { updateViaCache: 'none' })
```

- 每次发版递增版本号
- CDN 按完整 URL 缓存，新 URL 必然回源 → **从机制上绕开 CDN**
- `updateViaCache: 'none'` 禁止浏览器用 HTTP 缓存判断 SW 是否更新

### 第三层：服务端响应头分级

| 资源 | Cache-Control |
|---|---|
| html / sw / manifest | `no-cache, must-revalidate` |
| 图标、字体 | `public, max-age=31536000, immutable` |

不能一刀切 `no-store`，否则每次打开都全量下载。

附加：监听 `controllerchange` 自动 reload；页面可见时 + 每小时各触发一次 `update()`。

## 排查顺序（照这个走）

1. `curl` 线上页面，与本地 `md5sum` 对比 → 不同就是部署问题，**停下查部署，别继续猜**
2. `curl -I` 看 `cf-cache-status` / `age` / `cache-control` → `HIT` 说明被边缘缓存了
3. 看 `sw.js` 里的 `CACHE` 常量有没有变 → 没变，旧 cache 永远不会失效
4. 看注册 URL 有没有版本号 → 没有，这就是要补的第一件事
5. 最后才怀疑用户设备

## 经验

- **修复的关键不是「清缓存」，而是保证存在一条永远不被缓存的更新通道**（版本化 URL）
- 引入 SW 时就该带版本号，成本几乎为零，收益是永久免疫 CDN 缓存
- 为了「离线可用」而选「缓存优先」，代价可能是一次完整的线上故障。除非产品明确要求弱网优先，**默认用网络优先**
- 发版后自查：手机端打开一次，确认页脚版本号变了，才算发版完成
