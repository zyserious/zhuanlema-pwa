# 多端数据同步与冲突防护

> 目标：多台设备 + 一个云端，任何一台设备的空白/过时数据都不能覆盖掉完整数据。

## 问题长什么样

- 现象 A：手机端登录后看到全新的默认数据（用户以为数据丢了）
- 现象 B（更严重）：云端那份完整数据**被手机的空白数据覆盖**，记录全没了
- 用户只会说一句：「我在手机端账号登进去，为什么数据是新的了」

## 三个设计缺陷叠加

### ① 自动保存污染了「最后修改时间」

页面每 5 秒把行情数据保存一次，而这条自动路径**也调用了 `markDirty()`**。
结果：只要页面开着，本机就永远是「有未提交改动，而且是最新的」。

### ② 只比时间戳判新旧

`localNewerThan(serverSaved)` 只看本机修改时间 > 云端保存时间。
手机刚打开，时间必然最新 → 判定「本机更新」→ **上传空白数据而不是拉取云端**。

### ③ 服务端零校验

`POST /api/data` 谁后写谁赢。把自己本地刚清空的数据推上去，云端就真没了。

三者叠加形成**死循环**：手机把云端清空 → 云端和手机一起变空 → 两边互相印证谁都不觉得异常 → 之后每次恢复云端，手机都拿旧「通行证」再覆盖一次。

## 四道闸（缺一道就会复发）

### 闸一：同步锚点 `syncAnchor{user, saved}`

每台设备记住「我上次和这个账号同步到哪一版」。
**没有锚点的设备一律先拉云端，禁止上传** —— 新设备永远没有发言权。

### 闸二：自动数据走独立通道

- 新增 `saveTick()`：tick / 行情这类机器生成的数据只写本地 + 走 `auto` 推送
- **不写 `lastEdit`** → 自动保存不再伪装成「用户改动」
- 服务端对 `auto` 只合并 `stock` 一个字段，且校验字段完整（防止半截数据冲掉历史），并且**不改 `saved` 版本号**

### 闸三：三重判定 `reconcile()`

按顺序判：

1. 有没有锚点？没有 → 只能拉
2. 有锚点，本机确实有未上传改动（`dirty` + `lastEdit` 比锚点新）→ 上传
3. 本机数据**是否比云端更丰富**（`dataScore`：记录条数、设置项数）→ 只有更丰富且更新时才允许上传（这是给「旧版本设备升级」留的一次性桥接）
4. 其余一律以云端为准

### 闸四：服务端版本校验 + 快照

- 写请求必须带 `base`（上次同步的版本号），与当前 `saved` 不符 → **409 conflict**，客户端改为拉云端
- 每次写入前 `snapshot_accounts()` 快照，保留 30 份、60 秒节流

## 核心认知

- **时间戳单独不足以判断新旧**，必须三个维度一起看：时间（谁更新）、完整度（谁更能代表真实状态）、同步关系（这台设备是否被授权写数据）
- **「谁是权威」必须在写代码之前定义清楚**。默认答案是「云端权威 + 设备需授权」，而不是「谁后写谁赢」
- **机器生成的数据和用户主动修改的数据必须走不同通道**。混在一起，任何防抖/节流/自动保存都会污染业务判定
- **用户数据事故的第一护栏是快照，不是逻辑**。逻辑再严密也会有 bug，快照是 100% 能救回来的那层
- **服务端校验必须独立于前端版本**：用户可能还在跑旧版页面，旧版没有防护逻辑

## 怎么验证

`tests/` 下 6 个场景，`bash tests/run.sh` 一条命令跑完：

| 场景 | 期望 |
|---|---|
| 手机首登（空白 + 无锚点） | 拉云端 |
| 手机乱点 1 天（数据比云端少） | 拉云端 |
| 手机停留很久（无锚点） | 不许覆盖 |
| 旧电脑升级（数据更丰富 + 更新） | 上传，带正确 `base` |
| 已同步 + 本机又改过 | 上传，带 `base` |
| 已同步 + 没改动 | 拉云端 |

测试用 `vm` 沙箱直接加载**真实前端脚本**，只 mock `fetch` 与 `localStorage`，不 mock 业务逻辑。

## 踩过的坑

验证线上写接口时，用了**自己构造的半截数据**（`stock:{cash:1}`），把云端股票历史曲线冲掉了，靠刚上线的快照整份恢复。

教训：**验证线上写接口，永远先 GET、原样回写；先确认有快照再动手。**

## 可迁移性

这套「锚点 + 完整度 + base 校验 + 快照」可以直接搬到任何「本地优先 + 云端同步」的应用：笔记、待办、记账、阅读进度。
